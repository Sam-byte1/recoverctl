# 真机测试报告（2026-11-07）

## 背景与方法说明

世杰要求"操控虚拟机做一次实际模拟测试，把问题存成 Markdown 文件"，针对的是他最新反馈的两个场景：恢复几百兆的大视频、批量恢复 4 张图片。

**重要说明：这次测试不是真正的鼠标点击 GUI 测试。** CC 没有能力真的在图形界面里点击按钮——`prlctl exec` 这条执行通道让命令以系统后台身份运行在一个非交互的会话里，连真实窗口的句柄都读不到（之前专门试过 Windows UI Automation，`FindAll` 完全找不到任何窗口），这是 Windows Session 0 隔离级别的结构性限制，不是权限或方法问题，详见 `AGENTS.md` 第 8 节。

这次测试改用**直接驱动恢复引擎本身**的方式：用和 GUI 完全相同的底层代码（`recoverctl.exe` CLI 工具，和 GUI 共享同一套 `engine/` 代码），真实创建文件、删除、扫描、恢复、哈希校验，模拟世杰反馈的两个场景。这样测出的是**恢复引擎本身是否正确**，不是"按钮好不好点"这类纯界面问题——后者仍然需要世杰本人或任何能实际操作这台电脑的人用真实鼠标点一遍才能确认。

测试环境：VM 内真实 NTFS 测试卷 `E:`（卷标 RECOVERY_TEST），全程未触碰世杰的真实 U 盘（`G:`）。

## T1：大文件恢复测试

**步骤**：在 `E:\` 创建一个 300MB、内容可复现（固定随机种子）的测试文件，记录 SHA256，删除，用 `recoverctl.exe scan E:` 扫描，再用 `recoverctl.exe recover E: <MFT索引> <输出路径>` 恢复，比对哈希。

**结果**：
- 扫描耗时：0.1 秒
- 恢复耗时：**约 3 秒**（300MB）
- 恢复出的文件哈希与原始文件**完全一致**

**过程中的一次误报，已排除**：第一次测试时哈希不一致，一度怀疑是真实 bug。但没有直接下结论，而是复现了之前（2026-11-07 早些时候"NTFS大文件恢复加固"那轮）已经验证过的现象——**VM 虚拟磁盘的写回缓存对大文件写入有明显的持久化延迟**，如果删除文件的时机早于数据真正落盘，读到的就是还没写完的旧内容，表现出来就像"恢复出来的内容是错的"。把等待时间从 45 秒加长到 150 秒后，哈希完全匹配。**这不是恢复引擎的 bug，是测试方法本身要给足等待时间**——这条教训已经记在 `AGENTS.md` 里，这次只是又踩中验证了一次。

## T2：批量恢复测试（模拟 4 张图片）

**步骤**：在 `E:\` 创建 4 个大小不同（3MB/5MB/4MB/6MB）、内容各不相同的测试文件模拟 4 张照片，全部删除，扫描后依次恢复每一个（模拟 GUI 里 `recoverBatch()` 内部"一个接一个处理"的真实逻辑），记录每一项耗时并校验哈希。

**结果**：

| 文件 | 耗时 | 哈希校验 |
|---|---|---|
| photo_a.jpg (3MB) | 0.03 秒 | ✅ 一致 |
| photo_b.jpg (5MB) | 0.07 秒 | ✅ 一致 |
| photo_c.jpg (4MB) | 0.05 秒 | ✅ 一致 |
| photo_d.jpg (6MB) | 0.07 秒 | ✅ 一致 |
| **合计** | **0.27 秒** | 全部一致 |

**结论**：4 个文件的恢复在引擎层面是毫秒级的，没有任何卡顿或异常。这强烈支持小树的判断——世杰看到的"恢复 4 张图片时好像卡住了"，根源更可能是 GUI 的工作线程排队问题（比如恢复开始前，用户点过其它文件的预览，预览请求还没处理完，真正的批量恢复要等排在前面的预览处理完才会真的开始跑，但 GUI 上显示的"正在恢复 0/4"是按钮点击的一瞬间就显示的，和 worker 线程真正开始处理是两件事），而不是恢复引擎本身卡顿。小树上一轮已经针对这个线程排队问题做了 GUI 层面的缓解（忙碌时预览改成提示"请稍候"，不再无声排队）。

## T3：深度查找"选择磁盘..."按钮路径验证

**步骤**：这次恢复进度反馈之前，CC 刚修复了"深度查找"页面选不了磁盘的 bug（新增"选择磁盘..."按钮）。这里补充验证该按钮生成的设备路径格式（`\\.\PhysicalDriveN`）是否真的能被引擎正确识别。

**结果**：对 VM 里编号为 3 的物理磁盘（真实可移动 USB 设备），直接用 `recoverctl.exe partitions \\.\PhysicalDrive3` 验证，成功解析出 MBR 分区表（1 个分区，偏移 1048576 字节，大小约 30GB）。**确认新按钮生成的路径格式是真实有效、可被引擎直接使用的**，不是只在 GUI 层面"看起来能选"但后端打不开。

## 次要观察（非 bug，记录备查）

### 1. MFT 槽位复用导致的路径显示异常

测试 T1 第一轮失败后，残留的测试目录删除重建时，扫描结果里出现了两条看起来很怪的记录：`路径=big_video.mp4\scan_out.txt`——看起来像是"scan_out.txt 存在于一个叫 big_video.mp4 的文件里面"，但 `big_video.mp4` 从来不是目录。

**根因**：这是已知的"MFT 槽位复用"现象（项目之前已经评估过，归类为 NTFS 删除机制本身的固有限制，不是本项目的 bug）的一个新表现形式——旧目录被删除后，它的 MFT 槽位被新的普通文件复用，路径重建逻辑按"MFT 索引查父目录名字"的方式工作时，就会把新占用这个槽位的文件名误当成路径的一部分显示出来。

**影响范围**：只有在"一个目录被删除、随后它的 MFT 槽位被另一个普通文件复用"这种小概率的真实场景下才会出现，不是这次改动引入的新问题，不需要专门修复，已经有通用的免责提示覆盖这一类情况。记录在此，方便以后再遇到类似"路径显示很怪"的反馈时，能直接对上号。

### 2. CLI 命令行参数语义：NTFS 用 MFT 索引，FAT32 用候选项序号

测试过程中，CC 自己第一次调用 `recover` 命令时就用错了参数（把 NTFS 候选项列表里 `[0]` 这个序号当成索引传了进去，实际 NTFS 需要传的是"MFT 索引=40"这个真实数值，和 FAT32/exFAT 用的"候选项序号"含义不同）。

**这不影响 GUI 用户**——GUI 内部用的是完整的 `CandidateItem` 对象，不会要求用户手动输入索引，这纯粹是 CLI 命令行参数设计上的一个容易踩的坑。记录在此，方便以后谁再用 CLI 做手工测试/排查时别重蹈覆辙。

## 给世杰的结论

1. **恢复引擎本身是可靠的**——大文件、批量小文件两个场景都在毫秒到秒级完成，内容逐字节正确，这次测试没有找到需要修的新 bug。
2. 你反馈的几个现象（进度不明确、预览卡住、批量恢复像卡住）**根源在 GUI 层面，不在恢复引擎**，小树上一轮的修复方向是对的，这次算是交叉验证确认。
3. 真正"点击按钮体验好不好"这类纯界面层面的确认，目前只有你自己（或任何能实际操作这台电脑的人）用真实鼠标点一遍才能做到——这是本次测试没有、也没法覆盖的部分，建议你有空的时候按平时的习惯走一遍最新的 `recoverctl-gui-v10`，重点感受一下进度提示和预览的新提示文案是不是符合预期。
