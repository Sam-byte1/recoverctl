## 1. 项目目标

做一款**体验流程良好**的 Windows 数据恢复软件，核心差异化不在"能不能恢复"（底层解析能力已有成熟开源方案打底），而在于：
- 恢复效果：优先走文件系统结构化解析（找回文件名/目录），而非只会裸雕刻
- 覆盖场景：误删除、格式化、分区丢失、坏道、BitLocker 加密盘、Windows 卷影副本历史版本
- 产品体验：扫描进度可视化、预览、搜索过滤、安全的只读操作心智模型
- 可商用：组件选型全部考虑闭源商用许可边界（见 MANIFEST.md）

## 3. 开发方法论：TDD + Walking Skeleton

**不是"UI 先做漂亮、后接功能"**，原因：这个项目最大的不确定性在底层解析引擎是否可行（libfsntfs 能否可靠识别已删除记录、碎片能否正确拼接），不在 UI 好不好看。工程上要优先验证风险最高的部分，而不是最后验证。UI 设计本身也依赖真实功能跑出来的数据形态（进度粒度、可预览的文件类型、支持的扫描模式），在功能落地前设计 UI 容易做无用功。

**采用 Walking Skeleton（行走的骨架）**：第一个里程碑不追求功能完整或界面美观，而是搭一个贯穿全部架构层、但功能极简的端到端闭环——哪怕界面只是命令行，只要能真实做到「读测试镜像 → 识别一个已删除文件 → 恢复出来 → 校验内容完整」。骨架跑通后，功能和 UI 都在这个已验证的骨架上做增量，而不是赌一个未知可行性的东西。

**架构上采用 functional core, imperative shell（函数式内核，命令式外壳）**：
- **内核（TDD 驱动）**：纯函数，固定输入输出，不碰磁盘 I/O。例如"给一段 MFT record 字节，判断是否已删除、解析出文件名"。这类函数适合先写断言（给定已知字节 → 期望输出），测试失败后再写最少代码让它通过。
- **外壳（不走 TDD，手动验证）**：读磁盘、调 Windows API、画界面——负责把真实世界的脏数据喂给内核，把内核结果显示出来。

**测试夹具（fixtures）策略**：与普通应用开发不同，这里的"正确答案"必须是真实的磁盘字节结构，不能用 mock。需要准备小的真实测试镜像（如几十 MB 的 NTFS/FAT 卷镜像，人为删除已知文件并记录原始内容哈希），和"预期恢复结果"一起存进仓库，作为 TDD 的固定数据源。这件事在开始写解析逻辑之前就要准备好。

## 4. 开发环境路线

本项目主力开发机是 Mac，分阶段使用不同环境：

| 阶段 | 环境 | 覆盖内容 |
|---|---|---|
| P0-P2 核心引擎 TDD（Mac 本地部分） | Mac 原生（跨平台编译 libyal + 自研解析逻辑，对镜像文件测试） | 不需要 Windows，核心解析逻辑测试对象是镜像文件而非真实设备——**这部分截至 2026-11-05 凌晨已完成**（NTFS/FAT32/exFAT + GPT/MBR，详见 §8 和开发日志） |
| 现在（真实磁盘 I/O、VSS、UI、签名）—— **2026-11-04 起环境已就绪，2026-11-05 凌晨已完成真实设备验证这一段** | Mac + Parallels Desktop（Windows 虚拟机）+ USB 直通 | 覆盖 U 盘/SD 卡/移动硬盘等主流恢复场景的真实测试；NTFS/FAT32/exFAT + GPT/MBR 分区偏移扫描已经在真实虚拟机磁盘上验证通过，VSS/UI/签名这几项还没开始 |
| 发布前 QA | 一台二手 Windows 实体机（不需要高配，用 USB 转 SATA/NVMe 硬盘盒方便插拔测试盘） | 真实坏道盘、系统内部磁盘恢复场景、SmartScreen/杀软真实环境反馈、最终硬件兼容性 |

虚拟机覆盖不了真实坏道盘、真实内部磁盘场景、杀软云端信誉这几类，这些留到发布前用实体机测试，不作为日常开发环境。

**2026-11-05（小树裁决第16步）补充的产品风险判断**：碎片化可行性验证本身暴露了一个此前没人注意到的真实缺口——`fat_reader_recover_file`/`exfat_reader_recover_file` 目前对所有候选项都无条件假设"数据连续存储"，如果真实世界里（不是我们人为构造的测试场景）遇到一个本来就非连续存储的已删除文件，现在会**静默**读出错误/不完整的内容，但照常报告"恢复成功"——这正是本项目反复强调过的红线（第11步 `aligned_device_reader` 重构就是在处理同一类"不能静默返回错误但看起来成功的结果"问题）。两个文件系统的正确应对方式不一样，不能用同一个方案套两边：
- **exFAT**：可以真正检测（`no_fat_chain` 标志删除后依然可靠）、也可以真正修复（第15步已验证链信息删除后完整保留）——所以 exFAT 这边的正确做法是**直接修对**（见上面"已排进下一轮"），而不是退而求其次只做"检测+警告"。能真正解决问题的时候，用警告敷衍过去是不负责任的
- **FAT32**：删除时会清零链上所有簇的 FAT 表项，这意味着**删除之后，我们没有任何信号可以分辨一个跨多簇的候选项在删除前是否连续存储**——"挑出疑似碎片化的候选项打标记"这个思路对 FAT32 不成立，因为压根没有"疑似"的依据，风险是对所有跨多簇的 FAT32 候选项均等存在、且不可区分。正确做法不是编造一个检测不出来的"检测器"，而是诚实地告诉用户这个限制本身：CLI 对所有跨多簇的 FAT32 候选项，在 scan/recover 输出里加一条通用提示，说明"该限制是 FAT32 删除机制本身导致的，无法通过软件检测某个具体文件是否命中"
